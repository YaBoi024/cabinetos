# Games draw on the GPU the screen is on

- **Decided:** On a PC with two GPUs, games draw on the GPU the screen is wired to: the Vulkan device whose UUID matches the frontend's GL context's, for the libretro cores and for every emulator the frontend tells a device (Cemu, Xenia, sm2-emu, xemu). No match, or no way to ask, keeps the old order, a discrete card first. The emulators that pick a device for themselves (PCSX2, Eden, RPCS3, Vita3K, Play!) draw in windows of their own and are not told. A PC with one GPU is unchanged.
- **Date:** 2026-11-06
- **Why:** A core's picture reaches the UI's texture by importing the memory it drew into, which Vulkan defines only within one device; the old order put a two-GPU laptop's cores on the card the screen was not on, and the console died in an N64 game. The other ways: copying the picture across GPUs every frame (a dmabuf with modifiers and a copy through system memory: large, slow, fragile), or turning the second GPU off at boot (a guess, wrong with the monitor on a card). What it costs: on a laptop's own screen the games lose the big card for the integrated chip, slower at the GameCube picture levels and never a crash; a television on the laptop's HDMI port, usually wired to the card, gets the card. The rule names no brand, model or ID table, so it holds on every machine and changes nothing on one with one GPU. Only a two-GPU machine can prove it and the project has none; the tester proves it after it ships.
- **Numbers:** #659, "Two GPUs: a game draws on the GPU the screen isn't plugged into, and the console crashed"; PR #661, "Games draw on the GPU the screen is on".
- **Replaces:** the order "a discrete card first, then anything that is not software" in `gpu.cpp` and `vkhost.cpp`, kept as the fallback.
